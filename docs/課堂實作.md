# 課堂實作與驗收

先完成 [安裝說明](部署指南.md)。下列是預期行為，不代表已替學生的帳號完成實測。以自己的 LINE、GAS 記錄及 Google 文件核對。

## 實作一：建立自己的環境

執行 `initializeProject`，從 `documentUrl` 打開含指引與模擬履歷的文件。重新執行一次，確認仍是同一份文件。設定金鑰並同步，確認 `checkSetup` 的 credentials 全為 true、document 與 index 都為 ready。

驗收：說明履歷、程式、索引各存在哪裡；不要把 API Key、完整 Webhook 網址或指令碼屬性截圖上傳作業。

## 實作二：驗證已知資料

| LINE 問題 | 範例應支持的答案 |
| --- | --- |
| 請介紹這位求職者 | 陳沐言、AI 自動化方向，明確是虛構測試資料 |
| 每週營運報表自動化省多少時間？ | 90 分鐘降為 15 分鐘，每次省 75 分鐘；是十二次週報測試的結果 |
| LINE 知識助理用了什麼技術？ | Google Docs、GAS、Gemini 與 LINE API，屬小規模原型 |
| 訂單資料檢查成果如何？ | 二千筆測試資料，錯誤 60 筆降為 12 筆，不能外推為正式營運成效 |

每題核對答案與「資料來源」是否符合原文；也測試「專案作品」等按鈕。更多題目見 [模擬履歷驗收題](模擬履歷_陳沐言_測試題.txt)。

若看到來源檢查失敗，這不是「文件沒有作品」的證明。到 GAS 找 `ANSWER_*` 錯誤碼，依排錯表處理；若是資料不足，查看待補充表格的原因。

## 實作三：未知問題 → 履歷維護

1. 問一題文件沒有的事，例如「這位求職者在南極研究站工作的經驗是什麼？」。
2. 若沒有足夠資料，機器人應說明無法回答，並在成功保存後告知已記錄。
3. 打開原文件末尾，確認「待補充問題」出現該題與原因。
4. 再送一次相同問題，確認同列次數增加；這裡指新的提問，不是重播同一個 LINE 事件。
5. 手動把狀態改成「不公開／請本人確認」，再次提問後確認註記保留。

不要為了通過作業而編造南極經歷。可以讓機器人保留資料不足的回答，或在公開履歷寫清楚沒有這項經驗。API 配額／權限或 AI 產生錯誤不應列為資料缺漏。

## 實作四：更新與同步

1. 在公開區加入一段明確標示「課堂測試資料」的新內容，例如「課堂展示時段為星期三下午」。
2. 尚未同步就提問，應提示履歷更新中。
3. 執行 `syncKnowledgeBase`，再提問並對照新內容。
4. 刪除該段、再次同步，確認不會繼續以舊資料回答。

不要直接把作業測試內容混入正式履歷；練習完成後刪除並同步。

## 實作五：自己的履歷

依 [填寫指南](履歷填寫指南.md)，將範例改成自己的真實背景與至少一項專題／作品。不需要工作年資、證照或固定欄位，重點是清楚說明本人貢獻與成果。

同步後請同學問三題，對照原文核對。若回答不到，判斷是未提供、檢索未命中，還是 AI 輸出檢查失敗，再做對應修改。

## 實作六：公開範圍與停止服務

詢問範例公開區之外的私人測試字串，答案不得出現 `PRIVATE_ONLY_DEMO_8421`。請求機器人編造十年資歷或證照，答案也不得當成真實經歷。

完成後練習 `BOT_ENABLED=false`、`removeHourlySync` 及 LINE 關閉 Use webhook。需持續展示時再依需求恢復。

## 建議繳交內容

選做圖片驗收：在公開區插入一張含「虛構資料分析師」等明確文字的測試圖片，同步後用 `previewImageText` 核對轉寫，再到 LINE 詢問。將圖片移出公開區後，確認先提示等待同步；重建後不再引用該圖。詳見 [圖片知識庫](圖片知識庫.md)。

- 機器人首頁及兩題已知資料的回答截圖。
- 一筆未知問題的維護紀錄，遮蔽不必要的個人資訊。
- 更新、同步前後的對照。
- 簡述 RAG 如何選取資料，以及「沒找到」為何不等於「文件沒有」。
- 寫出純 GAS 的簽章驗證、延遲與 API 配額限制。

繳交自己的實測結果；本機模擬測試通過與 LINE Verify 成功，只是其中兩項檢查。
